`app.py`가 제목 아래 페이지 메뉴와 공통 필터를 준비합니다. `pages/01_overview.py`는 분쟁별 카드와 지도, 선택한 범주의 세부 명칭을 표시합니다. 연간·월간·주간 화면은 `ui/period_view.py`를 호출합니다. 데이터는 `data`, 집계 함수는 `services`, 페이지별 선택값과 변경 콜백은 `utils/state.py`에서 관리합니다.

데이터 처리 흐름은 `db_loader.read_tables_from_db()` → `detail_service.build_reports()` → `analysis_service.build_dashboard_data()`입니다. `snapshot.load_dashboard_snapshot()`은 서버 프로세스의 공유 `SnapshotStore`에서 완성된 결과를 반환합니다. 원본 판정 조인, 일별·월별 판정 집계, Overview 요약, 사전 명칭과 CSV는 데이터 버전마다 한 번만 준비합니다.

화면 구성과 기사 패널 내용은 Python에서 생성합니다. `ui/frontend`의 JavaScript는 지도·Plotly 클릭 전달, 점 옆 말풍선 위치, 도넛 라벨 연결선, 도넛 사용 조각의 기사 조회, 말풍선의 닫기·키보드 조작과 워드클라우드 영역 크기 측정을 처리합니다. 이 동작은 브라우저 DOM이 필요하므로 유지하며, JavaScript 패키지 설치나 Node 빌드 과정은 없습니다.

실제 DB 적재 스키마, UCDP·GDELT 수집 준비, 전처리 스크립트와 산출물은
별도 `conflict-defense-data-pipeline` 프로젝트에서 관리합니다. 앱은
접속 설정에 지정한 MySQL DB의 여섯 테이블을 읽기 전용으로 조회합니다.

## 대시보드 실행

화면은 **`.streamlit/secrets.toml`에 지정한 MySQL DB**를 조회합니다.
DB 이름은 코드에 고정되어 있지 않으므로 `dashboarddb`, `dashboarddb_dev_v1` 등
각자의 로컬 스키마 이름을 사용할 수 있습니다. 분쟁·월·유형·범주 필터에 따라
DB 데이터에서 지표를 계산합니다.

프로젝트 루트의 `.streamlit/secrets.toml`을 생성하거나 수정하고,
`[connections.dashboarddb]`의 `url`에 본인의 계정·비밀번호·호스트·포트·DB 이름을 설정합니다.
로컬 스키마 이름이 `dashboarddb`인 경우의 예시입니다.

```toml
[connections.dashboarddb]
url = "mysql+pymysql://dashboard_reader:CHANGE_ME@localhost:3306/dashboarddb?charset=utf8mb4"
```

`dashboard_reader`와 `CHANGE_ME`는 실제 접속 계정과 비밀번호로 바꿉니다.
스키마가 `dashboarddb_dev_v1`이면 URL의 `/dashboarddb?` 부분을
`/dashboarddb_dev_v1?`로 바꿉니다. **`[connections.dashboarddb]`는 앱이 읽는
설정 키이므로 실제 스키마 이름과 관계없이 그대로 유지합니다.**
비밀번호에 URL 예약 문자가 있으면 URL 인코딩합니다. 실제 설정 파일은 Git에서 제외합니다.

현재 브랜치를 받은 뒤 프로젝트 루트에서 의존성을 설치하고 실행합니다.
기존 `db` 브랜치를 사용하던 환경도 현재 의존성 목록에 맞춥니다.

```bash
conda activate streamlit
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

`streamlit` Conda 환경이 없다면 Python 3.13 환경을 먼저 준비합니다.
접속 설정 변경 후에는 앱을 재시작합니다.

**접속 설정만 바꿔 실행하려면 로컬 DB의 테이블·컬럼·데이터 규칙이 현재 로더와
같아야 합니다.** 특히 현재 로더는 `0=비사용, 1=사용, 2=불확실`을 기대합니다.
다른 코드 체계의 DB는 연결되더라도 검증 오류나 잘못된 집계가 발생할 수 있으므로
판정 코드의 의미가 위 정의와 일치하는지 먼저 확인해야 합니다.
자세한 규칙은 아래 **DB 조회와 캐시**를 참고하세요.
같은 페이지 구성을 사용하더라도 표시 수치는 각 로컬 DB의 데이터에 따라 달라집니다.

### 팀 개발 환경과 코드 규칙

개발 환경은 Python 3.13을 기준으로 합니다. Python 코드는 **Ruff 0.16.8**, **스페이스 2칸**, **작성한 따옴표 유지**, **줄 길이 기준 88자**, **LF 줄바꿈**으로 정리합니다. `pyproject.toml`에는 Python 버전, 들여쓰기, 따옴표 유지, 줄바꿈과 검사할 규칙만 설정합니다. 줄 길이 88자와 스페이스 들여쓰기 방식은 Ruff 기본값을 사용합니다.

파일 첫 줄의 `'''내용'''`은 Python에서 주석이 아닌 모듈 docstring입니다. Ruff는 `quote-style = "single"`이어도 docstring을 `"""내용"""`으로 정리하므로, 작은따옴표 세 개를 유지하려면 `"preserve"`가 필요합니다. 이 설정은 편집기 저장과 터미널에 공통으로 적용됩니다. 자세한 동작은 [Ruff의 quote-style 문서](https://docs.astral.sh/ruff/settings/#format_quote-style)를 참고하세요.

프로젝트 루트에서 개발 도구를 설치합니다. `requirements.txt`는 앱 실행 패키지, `requirements-dev.txt`는 개발용 Ruff만 관리합니다. 개발 환경에서는 두 파일을 함께 설치할 수 있습니다.

```bash
conda activate streamlit
python -m pip install -r requirements.txt -r requirements-dev.txt
```

- `pyproject.toml`이 팀 공통 규칙입니다. 기본 오류·미사용 변수 및 import를 검사하고 import 순서를 정리합니다. 프로젝트 내부 모듈은 Ruff가 자동으로 인식합니다.
- VS Code에서는 Ruff 확장을 설치하고 위 도구를 설치한 Python 환경을 선택합니다. 프로젝트 설정이 Python 기본 포맷터를 Ruff로 지정하며, 저장 시 포맷과 수정 가능한 오류·import 순서 정리를 실행합니다.
- 확장은 선택한 환경의 Ruff를 우선 사용하고 프로젝트 설정 파일을 우선 적용합니다. Ruff 버전은 `requirements-dev.txt`에서 관리합니다.
- `.editorconfig`를 지원하는 편집기는 Python 입력 시에도 2칸 들여쓰기를 사용합니다. 다른 편집기를 사용해도 아래 터미널 명령으로 동일하게 검사할 수 있습니다.

자동 정리와 수정 없는 검사는 다음 명령을 사용합니다.

```bash
# 자동 정리: 코드 오류와 import 순서를 먼저 수정한 뒤 포맷을 적용한다.
python -m ruff check --fix .
python -m ruff format .

# 검사만 실행: 원본 파일을 수정하지 않는다.
python -m ruff check .
python -m ruff format --check .
```

Ruff 버전을 올릴 때는 `requirements-dev.txt`를 변경하고 전체 검사를 실행합니다.

### 페이지 구성

| 파일                             | 화면                                    |
| -------------------------------- | --------------------------------------- |
| `pages/01_overview.py`           | 분쟁별 주요 범주, 지도와 선택 명칭, 지표 |
| `pages/02_annual.py`             | 방산 무기·기술 연간 분석                 |
| `pages/03_monthly.py`            | 방산 무기·기술 월간 분석                 |
| `pages/04_weekly.py`             | 방산 무기·기술 주간 분석                 |

`app.py`에서 종합 분석·연간 분석·월간 분석·주간 분석 네 페이지를 제목 아래 메뉴에 등록합니다.

- Overview는 등록 데이터의 첫 날짜부터 마지막 날짜까지 무기·기술을 함께 집계하며, 제목의 라벨 없는 드롭다운에서 분쟁만 선택합니다. 월간 분석의 월 선택은 `2026년 9월`로 표시하며 저장값은 `YYYY-MM`을 사용합니다.
- Overview의 `언급 기준 분석 기사 수`는 `articles`와 `conflicts`를 `conflict_id`로 내부 조인한 A의 분쟁별 행 수이며, `result`가 없는 기사도 포함합니다. 전체 선택 시 분쟁별 행 수를 합산합니다. 카드의 보도 사례 건수와 지도 수치는 사용 판정인 `result`를 `articles`·`conflicts`에 연결한 B에서 분쟁별 고유 `article_id` 수를 집계합니다. `사용 사례 포함 보도 수`는 전체 선택 시 B 전체의 고유 기사 수, 특정 분쟁 선택 시 해당 카드의 보도 사례 건수입니다. 무기·기술의 여러 범주에 같은 기사가 있어도 한 번만 세고, 동일 URL의 서로 다른 기사 ID는 각각 셉니다. 사용 판정은 DB 원본 `usage_code=1`, 정규화 후 `UsageCode.USED`입니다.
- 통합 연간·월간·주간 화면은 각각 연도·월·월요일~일요일 주 하나를 선택하며, 가장 최근 기사가 속한 기간이 기본값입니다. 연간 추이는 월별, 월간·주간 추이는 일별이고 빈 날짜는 0건으로 표시합니다. 무기와 기술을 합쳐 최대 5개 범주를 선택하며 첫 표시에는 사용 보도 수 상위 3개를 선택합니다.
- 분쟁·기간·유형·범주·검색어는 페이지별로 독립 저장·복원됩니다. 기간 화면의 초기화는 범주 선택과 검색어도 복원합니다.
- 분류 기준 CSV 다운로드는 Overview 분석 지표 아래의 `방산 무기·기술 분류 기준 CSV 다운로드` 영역에서 제공합니다. 버튼은 `SIPRI 무기 분류 기준(25개)`, `NATO 기술 분류 기준(42개)`이며 개수는 실제 분류 수에서 계산합니다. CSV는 모든 범주와 세부명칭을 `분류, 세부명칭` 열과 UTF-8 BOM으로 제공하며 분쟁 선택에 영향을 받지 않습니다.
- 통합 연간·월간·주간의 `기사 CSV 다운로드`는 상단 분쟁·기간·유형 필터만 적용합니다. 범주 선택과 관계없이 사용·불확실·비사용을 기사·범주 쌍당 한 행으로 내보냅니다. 열은 `기사 ID, 보도일, 제목, 국가간 분쟁, 무기/기술, 범주 ID, 범주명, 사용 판정, 근거 문장, 원문 URL`이며 보도일 내림차순·기사 ID·범주 ID 순으로 정렬합니다. UTF-8 BOM과 `YYYY-MM-DD` 날짜를 사용하고 빈 결과에도 헤더를 제공합니다. 클릭할 때 현재 화면의 스냅샷에서 생성해 조건별로 캐시하며 앱 재실행·DB 재조회·전체 정제를 하지 않습니다. 파일명은 `articles_{페이지}_{시작일}_{종료일}.csv`입니다.
- 타이틀과 메뉴는 스크롤 중에도 상단에 고정되며, 메뉴는 콘텐츠 너비로 왼쪽 정렬하고 좁은 화면에서는 줄바꿈합니다. 공통 필터 라벨은 `국가간 분쟁`, `무기/기술`입니다.
- Overview는 주요 분쟁 카드와 오른쪽 지표·지도·명칭 영역을 1:1로 배치합니다. 분석 지표는 내용 높이에 맞추고 지도와 16px 간격을 둡니다. 각 카드의 사용 보도 사례 건수는 분쟁명 오른쪽에 표시합니다. 오른쪽 영역의 컨테이너는 테두리 없이 표시합니다. 주요 무기·기술 태그는 라벨 오른쪽에 놓고 보도가 없는 유형의 행은 숨깁니다. 기존 지도 영역은 왼쪽 `국가간 분쟁 지도`와 오른쪽 워드클라우드를 1:1로 배치합니다. 지도와 이미지 영역은 각각 250px 높이이며, 좁은 화면에서는 세로로 배치합니다. 지도 아래는 처음에 비어 있으며 범주 태그를 선택할 때 사전의 세부 명칭을 표시합니다. 태그에는 해당 범주의 사용 확인 기사 수를 표시합니다. **사용 보도가 1건 이상인 분쟁만** 마커와 카드로 표시합니다. 마커 팝업의 연간 분석·월간 분석·주간 분석 버튼은 **분쟁만** 목적 페이지에 적용하고 기존 기간·유형·범주 선택은 유지합니다.
- 지도 팝업은 분쟁명·사용 보도 건수와 12px 분석 이동 버튼만 표시합니다. 20px 삼각형 꼬리의 끝점은 마커 중심에 연결되며 가장자리 팝업은 지도 내부 시점을 보정합니다. 팝업을 열면 안정적인 분쟁 ID로 연결된 카드 전체를 강조하고 분쟁 목록 내부만 스크롤합니다. 다른 마커를 선택하면 강조를 옮기고 닫으면 해제합니다. 특정 분쟁 필터는 팝업과 강조를 유지하고 지도 이동·확대·축소·마커 토글·닫기를 차단하며 줌 버튼을 숨깁니다. 전체 필터는 표시되는 마커가 하나여도 탐색할 수 있습니다. iframe 출처·조회 컨텍스트·분쟁 ID가 현재 화면과 일치하는 메시지만 처리합니다.
- 첫 접속의 데이터 조회·집계 중에는 중앙 스피너와 `대시보드를 불러오는 중…`을 표시합니다. 데이터 준비가 끝나면 화면을 표시하고 지도는 iframe·Leaflet 준비 완료, 도넛·추이는 Plotly 렌더링 완료, 워드클라우드는 이미지 로드·크기 일치 시 각각 영역 로딩을 해제합니다. 영역 높이를 미리 확보하고 별도 대기나 표시 지연을 추가하지 않습니다. 필터·범주·기사 페이지 변경에는 중앙 로딩을 다시 표시하지 않으며, 오류·빈 데이터·컴포넌트 제거 시 상태와 이벤트를 정리합니다. 동작 줄이기 설정에서는 스피너 회전을 생략합니다.
- 통합 기간 화면은 왼쪽 분석 영역과 오른쪽 기사 목록을 7.2:2.8로 배치합니다. 왼쪽 상단의 범주 선택·판단 분포는 2:5.2 비율과 420px 높이를 유지하며, 아래 추이의 오른쪽 끝은 판단 분포와 일치합니다. 기사 목록은 상단부터 추이 하단까지 채우고 제목·조회 조건·페이지 버튼은 고정하며 기사 카드만 내부 스크롤합니다. 화면 너비가 1000px 이하이면 범주 선택 → 판단 분포 → 추이 → 기사 목록 순서로 배치하고 기사 목록은 420px 높이를 유지합니다. 도넛은 선택 개수와 무관하게 지름 130px, 차트 공간 224×140px을 사용합니다. 제목 오른쪽에 사용·불확실·비사용 공통 범례를 한 번 표시하고 중앙 총건수는 굵은 15px 글자로 표시합니다. 도넛은 최대 3개까지 한 줄, 4개는 2×2, 5개는 위 3개·아래 중앙 2개로 가운데 정렬하며, 패널이 좁으면 한 열로 펼치며 데스크톱에서는 도넛 영역 안에서 스크롤하고, 모바일에서는 콘텐츠 높이에 맞춰 늘어납니다. 판정 비율은 조각 안에 표시하고 비사용 조각은 왼쪽에 둡니다. 내부 표시가 불가능한 비사용만 왼쪽 연결선을 사용하며, 작은 사용·불확실 비율은 차트 오른쪽 빈 공간에 판정색과 함께 표시합니다. 보도가 없는 범주도 같은 공간에 0건으로 남깁니다. 도넛의 사용 조각을 클릭하거나 키보드로 선택하면 해당 범주의 현재 선택 기간 전체 기사를 표시합니다. 불확실·비사용 조각은 기사 목록을 변경하지 않습니다. 사용 조각의 포커스 테두리는 표시하지 않으며 키보드 선택은 유지합니다.
- 범주 선택 목록은 사용 확인 기사 수 내림차순으로 정렬하고 0건 범주도 포함합니다. 검색으로 숨겨진 선택도 최대 5개 제한에 포함하며, 5개 선택 시 미선택 항목만 비활성화합니다.
- 세 분석 페이지의 선·점·범례는 선택된 범주 순서대로 주황 `#f97316` · 보라 `#a78bfa` · 분홍 `#f472b6` · 초록 `#4ade80` · 빨강 `#dc2626`을 사용합니다. 최대 5개 선의 색상이 겹치지 않으며 선택 변경 시 현재 선택 순서대로 다시 배정합니다.
- 선그래프 점을 클릭하면 해당 구간·범주의 기사 수, 증감 건수·증감률과 관련 기사 버튼을 표시합니다. 연간 화면은 전월 대비, 월간·주간 화면은 전일 대비입니다. 조회 첫 구간은 비교하지 않으며, 앞 구간이 0건이면 `신규` 또는 `변동 없음`으로 표시합니다.
- 관련 기사는 분석 영역 오른쪽의 상시 목록에 최신순으로 20건씩 표시합니다. 제목은 `{조회 범주명} 사용 관련 보도 목록`이며 별도 범주명 행 없이 긴 제목은 줄바꿈합니다. 선택 범주가 없으면 `사용 관련 보도 목록`을 표시합니다. 최초에는 현재 선택된 첫 번째 범주의 선택 기간 전체 사용 확인 기사를 조회합니다. 선그래프 점의 말풍선에서 `관련 기사 보기`를 누르면 연간은 해당 월, 월간·주간은 해당 날짜로 조회합니다. 전체 기간으로 다시 조회하려면 해당 범주 도넛의 사용 조각을 선택합니다. 범주·조회 기간·분쟁·총건수와 제목·발행일·분쟁·판단 근거·원문 링크를 제공하며 이전·다음으로 페이지를 이동합니다. 기사 ID 중복을 제거하므로 목록 총수는 도넛의 사용 건수 또는 선택한 점의 수치와 일치합니다. 기사 목록의 조회 범주는 분쟁·기간·유형·범주·데이터 버전 변경과 페이지 이동에도 유지하며, 새 조건에서는 같은 범주의 전체 기간·1페이지로 조회합니다. 유형 필터로 추이에서 숨겨진 범주도 목록의 조회 범주는 유지합니다. 검색어 변경만으로는 구간·페이지를 초기화하지 않습니다. 전체 범주 선택을 해제하거나 초기화 버튼을 누른 경우, 또는 조회 범주가 데이터에서 제거된 경우에는 선택 안내 또는 첫 선택 범주로 돌아갑니다. 범주 선택 없음과 조회 결과 없음은 각각 안내문을 표시합니다.
- 워드클라우드는 Overview에서만 표시하며, 선택한 분쟁과 전체 데이터 기간의 무기·기술 전체 사용 확인 범주를 집계합니다. 범주 태그 선택에는 영향을 받지 않습니다. 한글 범주명과 범주별 사용 확인 고유 기사 수의 제곱근을 배치용 가중치로 사용하고, 동명 범주의 표시 단어는 합산합니다. 같은 기사도 범주가 다르면 각각 집계합니다. 프로젝트에 포함된 **Pretendard Bold**로 서버에서 PNG를 생성하며, 이미지 영역의 실제 크기에 맞춰 글자 비율을 유지합니다.
- 보도 건수는 실제 사용 횟수나 성능을 의미하지 않습니다. 현재 DB의 판정은 기존 제공 예시에서 적재된 데이터입니다.

### 워드클라우드 스타일 변경

`ui/wordcloud_view.py`의 `WORDCLOUD_STYLE`, `WORDCLOUD_COLORS`, `WORDCLOUD_EMPHASIS`, `WORDCLOUD_LAYOUT_ATTEMPTS`를 수정하고 앱을 새로고침합니다. Overview 지도 오른쪽의 직사각형 전체에 단어를 촘촘히 배치합니다. 사전 생성용 기본 캔버스는 700×500이며 실제 화면에서는 부모 이미지 영역의 크기에 맞춰 최대 2048px, 기본 2배 해상도로 생성합니다. 최초 진입에서는 이미지를 생성하기 전에 부모 크기를 측정하며, 측정 크기에 맞는 이미지가 로드될 때까지 준비 중 표시를 보여줍니다. 처음 화면에 보이는 워드클라우드는 최종 배치이며, 기본 크기 이미지가 먼저 나타나는 현상을 방지합니다. 화면 크기 변경은 워드클라우드 프래그먼트만 갱신하며 기존 필터와 범주 선택을 유지합니다.

가로 배치 선호도는 0.65이며 일부 단어 전체를 90도 회전합니다. 글자 크기는 최소 12, 최대는 캔버스에 맞춰 자동 결정하며 단어 간 추가 간격은 0입니다. 서로 다른 시드로 3개 배치를 생성하고, 표시 단어 수·회전 단어 포함 여부·글자 점유 면적 순으로 비교해 결과를 고릅니다. 같은 범주를 반복하거나 임의의 단어를 추가하지 않습니다. 범주명 내부 공백과 글꼴 고유 자간은 유지합니다.

기사 수 상위 3개 범주는 기존 가장 밝은 하늘색 `#e0f2fe`로 강조하고, 동률은 범주명 순으로 정합니다. 나머지 범주도 기존 하늘색 팔레트에서 단어별 고정 색상을 사용합니다. 기사 수의 제곱근을 글자 크기의 가중치로 사용하며 정확한 건수는 범주 선택 목록에서 확인합니다.

이미지 캐시와 기본 화면 사전 로딩은 같은 배치 방식을 사용합니다. 캔버스 크기·배치 시도 횟수·모든 디자인 설정과 글꼴 파일의 SHA-256을 캐시 키에 포함하므로 크기나 설정이 바뀌면 다시 생성합니다. 글꼴 해시는 파일 수정 시각·크기가 바뀔 때만 계산하며 이미지 캐시는 최대 128개입니다. 기본 글꼴은 `assets/fonts/Pretendard-Bold.ttf`이며 프로젝트 기준 절대 경로로 읽습니다. AWS 배포 시 이 파일과 `OFL-Pretendard.txt`를 함께 포함하면 시스템 글꼴 설치나 실행 중 글꼴 다운로드가 필요 없습니다.

| 설정                             | 바뀌는 부분                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------- |
| `width`, `height`                | 초기 이미지 크기. 실제 화면은 부모 영역의 측정 크기를 사용                                                                 |
| `background_color`               | 배경색: 예를 들어 `'#ffffff'`                                                               |
| `min_font_size`, `max_font_size` | 최소·최대 글자 크기. 최대 `None`이면 캔버스에 맞춰 자동 결정                                                                         |
| `margin`                         | 단어 배치용 추가 간격. 기본값 `0`                                                           |
| `prefer_horizontal`              | 기본값 `0.65`. `1.0`이면 가로 배치, 낮추면 단어 전체의 90도 회전도 허용                                                |
| `relative_scaling`               | 기사 수 차이를 글자 크기에 반영하는 정도: `0`은 순위 위주, `1`은 빈도 비중을 더 강하게 반영 |
| `random_state`                   | 배치 패턴: 다른 정수로 변경하면 다른 배치 생성                                              |
| `max_words`                      | 표시할 최대 범주 수                                                                         |
| `font_path`                      | 한글을 지원하는 TTF/OTF 글꼴 경로                                                           |
| `WORDCLOUD_EMPHASIS`             | `weight_power`(0.5), `top_count`(3), `top_color`로 크기 가중치와 상위 범주 강조 조절 |
| `WORDCLOUD_COLORS`               | 글자색 목록: 예를 들어 `('#38bdf8', '#2dd4bf', '#fbbf24')`                                  |
| `WORDCLOUD_LAYOUT_ATTEMPTS`      | 배치 후보 수. 기본값 `3`, 표시 단어 수와 회전·점유 면적을 비교해 선택 |

범주 선택·도넛·기사 목록 영역의 너비는 `ui/period_view.py`에서, 지도·워드클라우드의 너비는 `pages/01_overview.py`의 `st.columns(...)`에서 조절합니다. 세부 옵션은 [WordCloud 공식 문서](https://amueller.github.io/word_cloud/generated/wordcloud.WordCloud.html)를 참고합니다.

### DB 조회와 캐시

`data/db_loader.py`는 필요한 컬럼만 명시해 아래 여섯 테이블을 조회합니다.

로더에서 내부 코드 **0=사용, 1=비사용, 2=불확실**로 변환하며 자동 감지하지 않습니다.
DB 코드 체계를 변경할 때는 `DB_USAGE_CODES`와 허용 범위 검증, 검증 테스트를
함께 변경해야 합니다.
유형은 `wp/tech`를 사용하고 외부 값 `weapon/technology`도 로더에서 변환합니다.

필수 컬럼·기본키·외래키·날짜·색상·좌표·판정 근거를 검증합니다.
기사 ID는 64비트 정수로 보존하고, 빈 제목은 상세 화면에서 `제목 없음`으로 표시합니다.
동일 URL은 서로 다른 분쟁에 속할 수 있지만 같은 분쟁 내 중복은 거부합니다.
분쟁은 ID의 숫자 부분과 ID 순서로 정렬합니다. 현재 DB에는 `display_order`가 없습니다.

연결 Engine은 지연 생성하여 재사용합니다. `st.cache_resource`가 서버 프로세스당 하나의
`SnapshotStore`를 관리합니다. 최초 조회에서 모든 공통 정제·집계와 세 분석 페이지의 기본
요약·추이와 Overview의 기본 워드클라우드를 준비한 뒤, 페이지 이동과 필터 변경에는 기존 스냅샷만 사용합니다.
새로운 조건은 작은 공통 집계에서 계산해 버전별 최대 128개 결과를 재사용하며 선택 범주는
범주 전체 요약과 워드클라우드 캐시 키에 포함하지 않습니다.

백그라운드 작업은 1시간 간격으로 별도 읽기 전용 트랜잭션에서 조회합니다. 내용이 같으면
조인·집계는 생략하고, 변경되면 완성된 스냅샷의 참조만 원자적으로 교체합니다. 갱신 중이나
실패 시 마지막 정상 스냅샷을 계속 사용하며 실패는 다음 주기에 재시도합니다. 새 버전은
사용자의 다음 페이지 이동·필터 조작에서 반영됩니다. `current()`는 완성된 스냅샷만 반환하며
`close()`와 리소스 해제 콜백은 갱신 작업을 중단합니다. 화면 자동 갱신 타이머는 없고
DB에 데이터 버전 테이블은 추가하지 않습니다.
정규화한 여섯 테이블의 내용 해시를 `revision`으로 제공하므로 제목·근거·기준 정보 변경도
지도와 기사 패널의 기존 클릭 컨텍스트를 무효화합니다.
최초 설정 누락·조회 실패·데이터 오류는 기존 오류 화면에서 안내합니다.

```python
from data.snapshot import load_dashboard_snapshot

snapshot = load_dashboard_snapshot()
tables = snapshot['tables']
```

스냅샷은 `tables`, `revision`, `reports`, `settings`, `article_daily`, `category_daily`를 유지하며
아래 데이터를 추가합니다. 공유 DataFrame은 수정하지 않고 필터 결과만 별도로 만듭니다.

| 데이터 | 행·컬럼과 재사용 영역 |
| --- | --- |

범주 이름에는 유형 접두사를 붙이지 않습니다. 같은 표시 이름은 워드클라우드에서 빈도를
합산하며 범주 선택·차트는 ID로 각각 관리하고 목록 도움말에 유형을 표시합니다.
Overview는 전체 데이터 기간을 사용하며 연간·월간·주간 화면의 기본값은 마지막 기사가 속한 기간입니다.
Folium HTML은 스냅샷 버전과 분쟁 조건별로 재사용하고 동일 HTML에서는 iframe을 다시
로드하지 않아 지도 확대·이동 상태를 유지합니다.

운영 화면에서 사용하지 않는 과거 시안·캡처·비교 HTML과 폐기된 집계 함수는 제거했습니다.
현재 메뉴에 연결된 네 페이지와 공통 코드, 자산·라이선스는 유지합니다.
새로 생성하는 로컬 시안과 검증 캡처의 `output/`은 Git에서 제외합니다.

#### 기존 원본의 DB 적재 전 정제 과제

### 코드 수정 위치

직접 작성하는 HTML은 `html_text = f'''...'''` 형태의 단일 문자열로 작성합니다.
첫 여는 태그는 `f'''`와 같은 줄에 놓고, 자식 태그는 2칸씩 들여쓰며 닫는 태그는
여는 태그와 정렬합니다. 반복 항목은 각각 템플릿으로 만든 뒤 합친 결과를 바깥 템플릿에
삽입합니다. HTML의 문자열 연결은 사용하지 않습니다. 변수 없는 정적 템플릿에는
해당 표현식에만 `# noqa: F541`을 붙여 `f` 접두사를 유지합니다. Plotly 라벨은
표시에 영향을 주는 공백을 추가하지 않으며, `%{...}` 치환 문법은 f-string 안에서
`%{{...}}`로 작성합니다. Folium 자동 생성 HTML과 JavaScript·Jinja 스크립트는 제외합니다.

### 검증

`tests/` 폴더는 페이지 렌더링에 필요하지 않아 유지하지 않습니다. 테스트용 파일은
임시 디렉터리에서 작성하고, 검증이 끝나면 테스트 파일과 관련 임시 산출물을 삭제합니다.

프로젝트 루트에서 문법·코드 규칙·포맷을 확인합니다. 이 명령들은 화면 동작까지 검사하지는 않습니다.

```bash
python -m compileall -q app.py config.py pages data services ui utils
python -m ruff check .
python -m ruff format --check .
```

프런트엔드 HTML/CSS/JavaScript는 등록 시 로드하므로 `ui/frontend/`를 수정한 뒤 Streamlit 서버를 재시작합니다. 컴포넌트는 자체 포털과 이벤트만 관리하고, 재렌더링·페이지 이동 시 정리합니다.

지도 화면은 넓은 화면에서 지도와 워드클라우드가 같은 너비·높이인지, 제목의 분쟁 선택에 따라 지표·지도·카드가 함께 바뀌는지 확인합니다. 좁은 화면에서는 영역이 세로로 이어지고 마커·말풍선·태그가 잘리지 않는지 확인합니다. 기간별 화면에서는 0~5개 선택에 따른 도넛 배치와 점의 기사 수·목록 총건수 일치, 기사 목록의 전체 높이와 고정 제목·내부 스크롤, 제목 여백과 긴 범주명을 확인합니다. 지도 중심·가장자리 마커의 꼬리 좌표, 팝업 전환·닫기와 카드 강조·목록 내부 스크롤, 특정 분쟁 잠금과 전체 필터 복귀를 확인합니다. 캐시 없는 접속·캐시 준비된 접속, 오류·빈 데이터·렌더링 중 페이지 이동에서 중앙·영역별 로딩이 정리되는지도 확인합니다.

## 프로젝트 개요

### 배경

- 러시아·우크라이나 전쟁의 드론 활용·대응기술과 이란 전쟁의 미사일·드론 공격 등이 최근 NATO·UN 자료에서도 다뤄지고 있어, 주요 분쟁에서 어떤 무기와 방산기술의 사용이 보도되는지 전쟁별·시기별로 비교할 필요
  - NATO NCIA (2026.09.09) : 우크라이나에서의 소형 드론 활용과 다중센서 기반 대드론 탐지·식별 기술 소개
  - UN (2026.03.03) : 미국·이스라엘의 대이란 공격 및 이란의 미사일·드론 반격 보도
- GDELT를 통해 다양한 해외 언론보도를 수집하고 주제별 기사량의 시간적 변화를 확인할 수 있어, 대상 분쟁의 관련 기사를 선별하고 무기·방산기술의 사용 보도 동향을 분석할 수 있는 데이터 기반 확보 가능
  - GDELT DOC 2.0 : 글로벌 온라인 뉴스의 검색 및 주제별 기사 건수·보도량의 시계열 분석 기능 제공
- 수집된 기사에 등장하는 무기·기술의 명칭과 분류를 통일하여, 사용이 보도된 무기·기술의 종류, 보도 빈도 및 기간별 변화를 일관된 기준으로 비교할 수 있는 분석 환경 마련 필요
  - SIPRI, _Arms Transfers Database – Sources and Methods_
  - 기술 분류는 NATO STO, Science & Technology Trends(2020)를 기본 자료로 하고, NATO, _Electromagnetic Warfare_(2023), NATO, _Summary of NATO’s Autonomy Implementation Plan_(2022), NATO, Summary of NATO’s Quantum Technologies Strategy(2024), NATO, Summary of NATO’s Revised Artificial Intelligence (AI) Strategy(2024) 의 관련 용어를 보완하여 구축한 프로젝트용 분석 분류체계

### 목적

  - https://www.nato.int/en/what-we-do/deterrence-and-defence/electromagnetic-warfare
  - https://www.nato.int/en/about-us/official-texts-and-resources/official-texts/2022/10/13/summary-of-natos-autonomy-implementation-plan
  - https://www.nato.int/en/about-us/official-texts-and-resources/official-texts/2024/01/16/summary-of-natos-quantum-technologies-strategy
  - https://www.nato.int/en/about-us/official-texts-and-resources/official-texts/2024/07/10/summary-of-natos-revised-artificial-intelligence-ai-strategy
- 각 전쟁에서 반복적으로 사용이 보도되는 무기·기술과 기간별 보도 빈도의 증가·감소를 직관적으로 비교·확인할 수 있도록 지원

## 프로젝트 수행 방향 및 내용

### 데이터 수집

1. SIPRI Arms Transfers Database – 무기 명칭·분류 데이터
   - 선정 사유 : 검증된 주요 재래식 무기의 명칭과 설명을 구조화하여 제공하므로 일관된 무기 분류 기준으로 활용하기에 적합
   - 수집 목적: 기사에 등장하는 무기 명칭을 표준 무기명과 분류에 연결하기 위한 무기 분류 Dictionary 구축
   - 수집 방법
     1. SIPRI Transfer Register 데이터를 CSV 형태로 수집
     2. `Weapon designation`과 `Weapon description`의 연결 관계를 추출하고 표기 차이·약어를 정리하여 `표준 무기명–무기 분류–검색용 명칭` 형태로 구성
2. NATO STO Science & Technology Trends 2020–2040 – 방산기술 기본 분류 데이터
   - 선정 사유: NATO 국방 과학기술 전문가 네트워크의 분석을 기반으로 주요 방산기술 범주를 체계적으로 제시하여 기술 분류 기준으로 활용하기에 적합
   - 수집 목적: 기사에 등장하는 방산기술 명칭을 공통 기술명과 상위 분류에 연결하기 위한 기술 분류 Dictionary 구축
   - 수집 방법
     1. NATO STO 기술전망 보고서의 8개 핵심 기술 분야를 대상으로 `Keywords`, `Technology Focus Areas`, 기술 정의 및 약어표에서 기술 용어 후보 추출
     2. 독립적인 기술 개념으로 사용할 수 있는 표현만 선정하고 기관명·정책명·국가명·연구 프로그램명 및 의미가 지나치게 넓은 일반 용어 제외
     3. NATO의 전자기전·자율체계·AI·양자기술 관련 공개자료에서 세부 기술과 운용 용어를 추가 추출
     4. 대소문자·하이픈·단수·복수 표기를 정규화하고 정식 명칭을 표준 기술명으로 지정하여 약어·표기 변형·한국어 번역명을 유의어로 연결
     5. 기존 용어와 추가 용어를 병합하여 `표준 기술명–상위 기술 분류–동의어·약어–한국어 번역명–출처` 형태의 기술 분류 Dictionary 구성
3. CAMEO Event Coding Dictionary 및 NATO 군사행동 정의 – 무기·기술 사용 여부 판별 데이터
   - 선정 사유: 위협·군사태세와 실제 공격·교전을 구분하는 정의와 사례를 제공하여 무기·기술의 사용 여부 판정 기준으로 활용하기에 적합
   - 수집 목적: 단순 언급·위협·계획과 실제 전투·방어·군사작전에서의 사용을 구분하기 위한 판별 Dictionary 구축
   - 수집 방법
     1. CAMEO에서 실제 군사행동과 사용 이전 단계에 해당하는 이벤트 코드 및 정의 수집
     2. 공개 Verb Pattern Dictionary에서 코드별 동사·구문을 추출하여 사용 포함·제외 표현 구성
     3. NATO 공개자료에서 전자전 등 방산기술의 운용 표현을 추가하여 `행동 유형–판별 표현–포함 여부–출처` 형태로 구성
4. GDELT 2.0 BigQuery – 해외 뉴스 기사 후보 데이터
   - 선정 사유: 다양한 해외 온라인 뉴스의 사건·출처·GDELT 처리 시각·원문 URL을 제공하여 수집 결과의 추적성 확보에 적합. 실제 기사 발행일은 원문에서 별도 확인
   - 수집 목적: 분쟁별·기간별 무기·방산기술 사용 보도 빈도와 변화 추이 분석을 위한 원천 기사 데이터 확보
   - 수집 방법
     1. UCDP의 국가 간 분쟁 목록과 검토가 필요한 잠정 후보를 구분하고, 2016~2026년 중 실행 시점까지 전체 기간을 한 번에 조회하는 분쟁별 검색 배치를 생성
     2. 공통 SQL에 각 배치의 기간·국가코드·행위자 검색어를 전달하고, `기간 AND (관련 지역 OR 행위자)` 조건으로 후보 조회. 매체·언어·이벤트 코드·추출 품질은 검토 정보로 보존
     3. `Events`와 `EventMentions`를 `GLOBALEVENTID`로 연결하여 웹 기사 URL을 확보하고, `batch_id`·`candidate_conflict_id`를 함께 저장
     4. 원문에서 실제 발행일과 해당 국가 간 직접 교전·무기 및 기술 사용 여부를 확인하여 내부 분쟁·일방적 폭력 등을 제외. 후보 분쟁 연결은 최종 판정 결과와 구분
     5. 기사 식별정보·원문 URL·사건 및 후보 분쟁 연결을 보존하고, 적용 SQL·파라미터·조회 기간·작업 ID·수집 일시를 기록하여 재현성 확보

### 데이터 전처리

#### 데이터 정제

- 수집된 원문은 별도로 보존하고 분석용 제목·본문 생성
- HTML 태그, 광고, 메뉴, 불필요한 공백·특수문자 제거
- 기사 URL 정규화 및 발행일·수정일·수집일 형식 통일
- 원문 미확보·필수값 누락·형식 오류 데이터에 처리 상태 부여

#### 데이터 통합

- 기사 식별정보 또는 정규화된 URL을 기준으로 GDELT CSV 메타데이터와 원문 기사 결합
- 검색 시 부여한 후보 분쟁 ID와 UCDP 당사자 정보를 참조하여 본문에서 직접 교전 관계를 확인하고 최종 분쟁 연결과 근거 저장
- 무기 분류 Dictionary, 기술 분류 Dictionary 및 사용 여부 판별 Dictionary 연결
- 무기와 기술을 독립적으로 매핑하고 한 기사에 여러 항목이 등장하는 경우 각각의 연결 관계 유지
- 기사 원문과 분쟁·무기·기술·사용 여부 판정 결과를 구분하여 저장

#### 데이터 축소

- 정규화된 URL이 동일하면 기사 원문은 한 번만 관리하되, 기사–GDELT 사건–후보 및 확정 분쟁 연결은 보존
- 정제된 본문이 동일한 재게시 기사 중 대표 기사만 유지
- 동일 기사의 수정본이 여러 건인 경우 최종 수정일이 가장 최근인 기사 유지
- 원본 후보와 처리 상태를 별도 보존하고, 원문 미확보 등 판정 불가능 데이터는 확정 집계에서 제외

#### 데이터 변환

- 국가·기관·무기·기술의 대소문자, 하이픈, 단수·복수, 약어 및 표기 변형 정규화
- 기사에서 발견된 무기·기술 명칭을 표준 ID와 상위 분류에 매핑하고 근거 문장 저장
- 사용 표현과 행위 주체의 연결 관계를 기준으로 `사용`, `비사용`, `불확실`로 분류
- 기사 전체가 아닌 `기사–분쟁–무기·기술 항목` 단위로 사용 여부 판정하여 다른 분쟁의 사용 근거가 섞이지 않도록 처리
- 개발·지원·계획·시험·위협 등 실제 사용 이전 단계는 `비사용`으로 변환

#### 데이터 필터링 및 정렬

- 실제 기사 발행일에 분석 기간을 적용하고, 원문 언어에 따라 영문 분석 또는 번역 처리. 적용 언어 범위와 번역 여부 기록
- 특정 매체 목록으로 초기 제한하지 않고 매체·추출 품질을 검토 정보로 보존
- 모든 대상 국가 간 분쟁에 동일한 직접 교전 기준을 적용하고, 내부 분쟁·비국가 분쟁·일방적 폭력·국내 정치·무기 공급 및 지원·대리세력 활동만 다룬 기사는 최종 사용 보도 집계에서 제외
- 대상 분쟁과의 관련성이 불명확한 기사는 `불확실`로 분리
- 분쟁 관련 기사 중 무기 또는 방산기술이 확인된 기사만 분석 대상으로 선정
- 분쟁·발행일·매체·표준 무기·기술 ID 순으로 정렬하여 분석 데이터 생성
