`app.py`가 공통 설정과 필터를 준비합니다. `pages/01_overview.py`에서 지도·분쟁별 요약·범주별 상세 명칭을 표시하고, 무기·기술 월간 페이지는 `ui/monthly_view.py`의 공통 화면 함수를 호출합니다. 데이터는 `data`, 집계 함수는 `services`, 페이지별 선택값과 변경 콜백은 `utils/state.py`에서 관리합니다.

데이터 처리 흐름은 `db_loader.read_tables_from_db()` → `detail_service.build_reports()` → `analysis_service.build_dashboard_data()`입니다. `snapshot.load_dashboard_snapshot()`이 이 결과와 설정을 묶어 캐시합니다. 원본 판정 조인은 한 번만 수행하며, 사전 명칭 표와 CSV는 `classification_details()`를 함께 사용합니다.

화면 구성과 기사 패널 내용은 Python에서 생성합니다. `ui/frontend`의 JavaScript는 지도·Plotly 클릭 전달, 점 옆 말풍선 위치, 기사 패널의 닫기·키보드 포커스에 한정합니다. 이 동작은 브라우저 DOM이 필요하므로 유지하며, JavaScript 패키지 설치나 Node 빌드 과정은 없습니다.

실제 DB 적재 스키마, UCDP·GDELT 수집 준비, 전처리 스크립트와 산출물은
별도 `conflict-defense-data-pipeline` 프로젝트에서 관리합니다. 앱은
접속 설정에 지정한 MySQL DB의 여섯 테이블을 읽기 전용으로 조회합니다.

## 대시보드 실행

화면은 **`.streamlit/secrets.toml`에 지정한 MySQL DB**를 조회합니다.
DB 이름은 코드에 고정되어 있지 않으므로 `dashboarddb`, `dashboarddb_dev_v1` 등
각자의 로컬 스키마 이름을 사용할 수 있습니다. 분쟁·월·유형·범주 필터에 따라
DB 데이터에서 지표를 계산합니다.

프로젝트 루트의 `.streamlit/secrets.toml`을 생성하거나 수정하고,
`[connections.dashboarddb]`의 `url`에 본인의 계정·비밀번호·호스트·포트·DB 이름을 설정합니다.
로컬 스키마 이름이 `dashboarddb`인 경우의 예시입니다.

```toml
[connections.dashboarddb]
url = "mysql+pymysql://dashboard_reader:CHANGE_ME@localhost:3306/dashboarddb?charset=utf8mb4"
```

`dashboard_reader`와 `CHANGE_ME`는 실제 접속 계정과 비밀번호로 바꿉니다.
스키마가 `dashboarddb_dev_v1`이면 URL의 `/dashboarddb?` 부분을
`/dashboarddb_dev_v1?`로 바꿉니다. **`[connections.dashboarddb]`는 앱이 읽는
설정 키이므로 실제 스키마 이름과 관계없이 그대로 유지합니다.**
비밀번호에 URL 예약 문자가 있으면 URL 인코딩합니다. 실제 설정 파일은 Git에서 제외합니다.

현재 브랜치를 받은 뒤 프로젝트 루트에서 의존성을 설치하고 실행합니다.
기존 `db` 브랜치를 사용하던 환경도 현재 의존성 목록에 맞춥니다.

```bash
conda activate streamlit
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

`streamlit` Conda 환경이 없다면 Python 3.13 환경을 먼저 준비합니다.
접속 설정 변경 후에는 앱을 재시작합니다.

**접속 설정만 바꿔 실행하려면 로컬 DB의 테이블·컬럼·데이터 규칙이 현재 로더와
같아야 합니다.** 특히 현재 로더는 `0=비사용, 1=사용, 2=불확실`을 기대합니다.
다른 코드 체계의 DB는 연결되더라도 검증 오류나 잘못된 집계가 발생할 수 있으므로
판정 코드의 의미가 위 정의와 일치하는지 먼저 확인해야 합니다.
자세한 규칙은 아래 **DB 조회와 캐시**를 참고하세요.
같은 페이지 구성을 사용하더라도 표시 수치는 각 로컬 DB의 데이터에 따라 달라집니다.

### 팀 개발 환경과 코드 규칙

개발 환경은 Python 3.13을 기준으로 합니다. Python 코드는 **Ruff 0.16.8**, **스페이스 2칸**, **작성한 따옴표 유지**, **줄 길이 기준 88자**, **LF 줄바꿈**으로 정리합니다. `pyproject.toml`에는 Python 버전, 들여쓰기, 따옴표 유지, 줄바꿈과 검사할 규칙만 설정합니다. 줄 길이 88자와 스페이스 들여쓰기 방식은 Ruff 기본값을 사용합니다.

파일 첫 줄의 `'''내용'''`은 Python에서 주석이 아닌 모듈 docstring입니다. Ruff는 `quote-style = "single"`이어도 docstring을 `"""내용"""`으로 정리하므로, 작은따옴표 세 개를 유지하려면 `"preserve"`가 필요합니다. 이 설정은 편집기 저장과 터미널에 공통으로 적용됩니다. 자세한 동작은 [Ruff의 quote-style 문서](https://docs.astral.sh/ruff/settings/#format_quote-style)를 참고하세요.

프로젝트 루트에서 개발 도구를 설치합니다. `requirements.txt`는 앱 실행 패키지, `requirements-dev.txt`는 개발용 Ruff만 관리합니다. 개발 환경에서는 두 파일을 함께 설치할 수 있습니다.

```bash
conda activate streamlit
python -m pip install -r requirements.txt -r requirements-dev.txt
```

- `pyproject.toml`이 팀 공통 규칙입니다. 기본 오류·미사용 변수 및 import를 검사하고 import 순서를 정리합니다. 프로젝트 내부 모듈은 Ruff가 자동으로 인식합니다.
- VS Code에서는 Ruff 확장을 설치하고 위 도구를 설치한 Python 환경을 선택합니다. 프로젝트 설정이 Python 기본 포맷터를 Ruff로 지정하며, 저장 시 포맷과 수정 가능한 오류·import 순서 정리를 실행합니다.
- 확장은 선택한 환경의 Ruff를 우선 사용하고 프로젝트 설정 파일을 우선 적용합니다. Ruff 버전은 `requirements-dev.txt`에서 관리합니다.
- `.editorconfig`를 지원하는 편집기는 Python 입력 시에도 2칸 들여쓰기를 사용합니다. 다른 편집기를 사용해도 아래 터미널 명령으로 동일하게 검사할 수 있습니다.

자동 정리와 수정 없는 검사는 다음 명령을 사용합니다.

```bash
# 자동 정리: 코드 오류와 import 순서를 먼저 수정한 뒤 포맷을 적용한다.
python -m ruff check --fix .
python -m ruff format .

# 검사만 실행: 원본 파일을 수정하지 않는다.
python -m ruff check .
python -m ruff format --check .
```

Ruff 버전을 올릴 때는 `requirements-dev.txt`를 변경하고 전체 검사를 실행합니다.

### 페이지 구성

| 파일                             | 화면                                          |
| -------------------------------- | --------------------------------------------- |
| `pages/01_overview.py`           | 기사 지표, 지도, 분쟁별 주요 범주와 상세 명칭 |
| `pages/02_weapons_monthly.py`    | 방산 무기 월간 분석                           |
| `pages/03_technology_monthly.py` | 방산 기술 월간 분석                           |

`app.py`에서 세 페이지를 상단 메뉴에 등록합니다. 무기·기술 월간 화면은 같은 `render_monthly()` 함수를 사용합니다.

- 시작월·종료월은 검색 가능한 `YYYY.MM` 드롭다운입니다. 시작월 기본값은 overview `2016.01`, 월간 분석 `2025.09`이며 종료월은 가장 최근 기사의 월입니다. 새 페이지 상태와 초기화에 기본값을 적용하고 기존에 저장된 유효한 기간은 유지합니다. 선택한 두 월을 포함해 월초부터 월말까지 집계합니다. 역전된 기간은 안내 후 집계를 중단합니다.
- 분쟁·기간·유형·범주·검색어는 페이지별로 독립 저장·복원됩니다. 초기화는 현재 페이지의 **분쟁·기간·유형만 복원**하며 범주 선택과 범주 검색어는 유지합니다. 기존 일 단위 저장값은 해당 월로 변환합니다.
- overview 필터 줄의 초기화 버튼 오른쪽에서 해당 유형의 **모든 범주와 세부명칭**을 CSV로 내려받습니다. `전체` 유형에서는 무기·기술 버튼을 따로 표시합니다. CSV는 `분류, 세부명칭` 열과 UTF-8 BOM을 사용하며 분쟁·기간 필터에 영향을 받지 않습니다.
- 지도와 주요 범주는 2:1로 배치합니다. 현재 분쟁·기간·유형에서 **사용 보도가 1건 이상인 분쟁만** 마커와 카드로 표시하며, 모두 0건이면 기본 세계 지도와 안내를 표시합니다. 원형 마커 크기는 동일 기간·유형의 전체 분쟁 기사 수를 기준으로 달라집니다. 마커 팝업의 월간 분석 버튼은 **분쟁만** 목적 페이지에 전달하고 기간·범주·검색어는 유지합니다. 분쟁 필터에는 14개 분쟁을 모두 유지합니다.
- 월간 범주는 최대 5개이며 **페이지별 첫 유효 렌더링에만 현재 정렬 목록의 앞 3개를 선택**합니다. **선택 목록만 현재 분쟁·기간의 사용 확인 고유 기사 수 내림차순**으로 정렬하고, 동률이면 이름순으로 정렬합니다. 0건 범주도 포함해 기본 3개를 채웁니다. 지도에서 처음 진입하면 전달받은 분쟁으로 계산합니다. 이후 검색·정렬·필터 변경·재방문·초기화에서는 선택값을 유지하며, 전체 선택 해제와 기존 버전의 저장 상태도 보존합니다. 선그래프 범례와 판정 분포의 순서는 유지합니다. 검색으로 숨겨진 선택도 제한 개수에 포함됩니다. 5개 선택 시 미선택 항목만 비활성화합니다.
- 선그래프 점을 클릭하면 해당 월·범주의 기사 수, 전월 대비 증감 건수·증감률과 관련 기사 버튼을 표시합니다. 조회 첫 달은 비교하지 않으며, 전월 0건이면 `신규` 또는 `변동 없음`으로 표시합니다.
- 관련 기사는 오른쪽 오버레이에 최신순으로 20건씩 표시합니다. 해당 분쟁·월·범주의 사용 확인 기사를 중복 제거하므로 목록 총수는 차트 수치와 일치합니다. 제목·발행일·분쟁·근거·원문 링크를 확인할 수 있으며 닫기·배경 클릭·Esc를 지원합니다.
- 판정 상태 분포는 분쟁·기간·선택 범주에 따릅니다. 범주는 y축에 표시하며 **막대 높이는 48px, 범주 간 간격은 12px로 고정**하고 표시 범주 수에 따라 차트 높이를 조절합니다. x축의 가로 분할은 `사용 / 불확실 / 비사용` 비율이며, 면적이 전체 판정 건수를 나타내지는 않습니다. 기사×범주 단위이므로 동일 기사도 범주마다 각각 집계합니다.
- 워드클라우드는 **범주 체크박스와 무관하게** 해당 유형의 전체 범주를 집계합니다. 범주 선택 목록과 동일한 한글 범주명을 단어로 표시하고, 범주별 사용 확인 고유 기사 수에 따라 글자 크기를 정합니다. 같은 기사도 범주가 다르면 각각 집계합니다. 전체 범주별 건수는 펼침 목록에서 확인할 수 있으며, 무기·기술 모두 프로젝트에 포함된 **Pretendard Regular**를 사용합니다. 서버에서 로컬 TTF로 PNG를 생성하므로 접속 기기의 글꼴 설치 여부에 의존하지 않습니다.
- 보도 건수는 실제 사용 횟수나 성능을 의미하지 않습니다. 현재 DB의 판정은 기존 제공 예시에서 적재된 데이터입니다.

### 워드클라우드 스타일 변경

`ui/wordcloud_view.py`의 `WORDCLOUD_STYLE`, `WORDCLOUD_COLORS`, `WORDCLOUD_ELLIPSE`를 수정하고 앱을 새로고침합니다. 스타일과 글꼴 파일의 SHA-256이 캐시 키에 포함되므로 같은 경로의 TTF를 교체해도 이미지를 다시 생성합니다. 기본 글꼴은 `assets/fonts/Pretendard.ttf`이며 프로젝트 기준 절대 경로로 읽습니다. AWS 배포 시 이 파일과 `OFL-Pretendard.txt`를 함께 포함하면 시스템 글꼴 설치나 실행 중 글꼴 다운로드가 필요 없습니다. 기본 배치는 추가 단어 간격 없이 캔버스 가로·세로의 80% 크기 타원 안에 글자를 배치한 뒤, 실제 글자 영역을 캔버스 정중앙에 옮깁니다. 범주명 내부 공백과 글꼴 고유 자간은 유지합니다.

| 설정                             | 바뀌는 부분                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------- |
| `width`, `height`                | 이미지 크기와 가로세로 비율                                                                 |
| `background_color`               | 배경색: 예를 들어 `'#ffffff'`                                                               |
| `min_font_size`, `max_font_size` | 최소·최대 글자 크기                                                                         |
| `margin`                         | 단어 배치용 추가 간격. 기본값 `0`                                                           |
| `prefer_horizontal`              | `1.0`이면 가로 배치, 낮추면 세로 배치도 허용                                                |
| `relative_scaling`               | 기사 수 차이를 글자 크기에 반영하는 정도: `0`은 순위 위주, `1`은 빈도 비중을 더 강하게 반영 |
| `random_state`                   | 배치 패턴: 다른 정수로 변경하면 다른 배치 생성                                              |
| `max_words`                      | 표시할 최대 범주 수                                                                         |
| `font_path`                      | 한글을 지원하는 TTF/OTF 글꼴 경로                                                           |
| `WORDCLOUD_COLORS`               | 글자색 목록: 예를 들어 `('#38bdf8', '#2dd4bf', '#fbbf24')`                                  |
| `WORDCLOUD_ELLIPSE`              | `width_ratio`, `height_ratio`로 타원 배치 영역 크기 조절. 기본값 각각 `0.8`                 |

페이지에서 워드클라우드 영역의 너비는 `ui/monthly_view.py`의 `mosaic_column, words_column = st.columns(2, ...)`에서 조절합니다. 예를 들어 `st.columns([1, 2], ...)`로 바꾸면 워드클라우드 영역이 두 배 비중을 차지합니다. 세부 옵션은 [WordCloud 공식 문서](https://amueller.github.io/word_cloud/generated/wordcloud.WordCloud.html)를 참고합니다.

### DB 조회와 캐시

`data/db_loader.py`는 필요한 컬럼만 명시해 아래 여섯 테이블을 조회합니다.
모든 조회는 하나의 InnoDB 읽기 전용 일관된 스냅샷 트랜잭션에서 실행합니다.
DB 스키마나 데이터를 수정하지 않으며, 화면에 쓰지 않는 `usage_patterns`는 조회하지 않습니다.

아래 행 수는 `dashboarddb_dev_v1`에서 2026-09-29에 확인한 값이며,
다른 로컬 DB에 요구되는 고정 행 수가 아닙니다. 검증 당시 판정은 기존 예시 판정과
동일하며, DB 연결 자체가 판정 정확성을 보증하지는 않습니다.

| 테이블             | 2026-09-29 연결 검증 시 행 수 |
| ------------------ | ----------------------------: |
| `conflicts`        |                            15 |
| `categories`       |          67 (무기 25·기술 42) |
| `sipri_dictionary` |                         4,540 |
| `nato_dictionary`  |                           155 |
| `articles`         |                       214,914 |
| `result`           |                        13,323 |

현재 로더가 요구하는 DB 판정 코드는 **0=비사용, 1=사용, 2=불확실**입니다.
로더에서 내부 코드 **0=사용, 1=비사용, 2=불확실**로 변환하며 자동 감지하지 않습니다.
DB 코드 체계를 변경할 때는 `DB_USAGE_CODES`와 허용 범위 검증, 검증 테스트를
함께 변경해야 합니다.
유형은 `wp/tech`를 사용하고 외부 값 `weapon/technology`도 로더에서 변환합니다.

필수 컬럼·기본키·외래키·날짜·색상·좌표·판정 근거를 검증합니다.
기사 ID는 64비트 정수로 보존하고, 빈 제목은 상세 화면에서 `제목 없음`으로 표시합니다.
동일 URL은 서로 다른 분쟁에 속할 수 있지만 같은 분쟁 내 중복은 거부합니다.
분쟁은 ID의 숫자 부분과 ID 순서로 정렬합니다. 현재 DB에는 `display_order`가 없습니다.

연결 Engine은 지연 생성하여 재사용합니다. 조회·검증·집계 결과를 함께 60초간 캐시하고,
캐시 만료 후 다음 화면 실행(필터 조작 또는 새로고침)에서 다시 조회합니다.
열린 화면을 자동 갱신하는 타이머는 없습니다. DB에 데이터 버전 테이블은 추가하지 않습니다.
정규화한 여섯 테이블의 내용 해시를 `revision`으로 제공하므로 제목·근거·기준 정보 변경도
지도와 기사 패널의 기존 클릭 컨텍스트를 무효화합니다.
설정 누락·조회 실패·데이터 오류는 화면에 안내하고 중단하며 로컬 파일로 대체하지 않습니다.

```python
from data.snapshot import load_dashboard_snapshot

snapshot = load_dashboard_snapshot()
tables = snapshot['tables']
```

스냅샷은 `tables`, `revision`, `reports`, `settings`, `article_daily`,
`category_daily`를 유지합니다. `services/`와 화면의 기사 상세·판정 분포·
워드클라우드·지도 연동은 같은 입력 구조를 사용합니다.
기본 시작월은 overview `2016.01`, 월간 분석 `2025.09`이며 종료월은 DB의 최신 기사 월입니다.

DB 없이 실행하는 회귀 테스트:

```bash
python -m unittest discover -s tests -v
```

### 분류 CSV의 빈 세부명칭

2026-09-29 확인 기준, 무기 25개 범주에는 모두 사전 명칭이 등록되어 있고 기술 42개 중 2개 범주에는 등록되어 있지 않습니다.
CSV는 모든 범주를 유지하면서 `category_id`로 사전을 연결하고, 연결된 명칭이 없는 범주의 `세부명칭`을 빈 값으로 저장합니다.
분쟁·기간과 관계없이 원본 사전의 등록 상태를 반영합니다.

| 유형 | 사전 등록 범주 | 미등록 범주 ID와 이름                     |
| ---- | -------------: | ----------------------------------------- |
| 무기 |        25 / 25 | 없음                                      |
| 기술 |        40 / 42 | `T0114` 플랫폼전자, `T0502` 내열/단열재료 |

`sipri_dictionary`의 4,540행과 `nato_dictionary`의 155행에서 명칭 자체가 빈 행이나
잘못된 범주 ID 연결은 발견되지 않았습니다. 위 두 기술 범주에는 연결할 사전 행 자체가 없습니다.
명칭을 채우려면 원본 사전에 검증된 명칭을 추가해야 합니다. 미등록된 배경은 현재 자료만으로 확인할 수 없습니다.

### 기사 지표 집계 기준

| 지표                             | 집계 기준                                                     |
| -------------------------------- | ------------------------------------------------------------- |
| 분석 기사 수                     | 판정 결과에 등장하는 고유 article_id 수. 내부 코드 0·1·2 포함 |
| 사용 보도 수                     | 선택한 유형에서 내부 코드 0인 고유 article_id 수              |
| 전체 유형                        | 무기·기술 기사 ID 집합의 합집합                               |
| 서로 다른 분쟁의 동일 URL        | 각 article_id를 별도 기사로 집계                              |
| 월별 추이·기사 목록·워드클라우드 | 사용 기사만 범주별로 중복 제거                                |
| 판정 상태 분포                   | 기사×범주 전체 판정 결과                                      |
| 분류 수                          | 등록 범주 수. 기간·분쟁과 무관                                |

현재 전체 기간의 분석 기사는 **11,531건**, 사용 기사는 **4,198건**, 분류는 **67개**입니다.
DB의 전체 수집 기사 214,914건 중 결과가 없는 기사는 분석 기사 수에서 제외합니다.
합계는 코드에 고정하지 않고 원본에서 계산합니다. 판정 행은 사용 4,778건·비사용 594건·불확실 7,951건입니다.

DB에는 방글라데시·미얀마, 콩고민주공화국·르완다와 미국·베네수엘라를 포함한
15개 분쟁이 등록되어 있습니다. 원본·전처리 산출물과 fixture 생성 도구는
`conflict-defense-data-pipeline` 프로젝트에서 관리합니다.

화면용 반환 컬럼은 기존과 같습니다.

- 기사 지표: `date, conflict, kind, analysis_articles, usage_articles`.
- 범주별 사용 보도: `date, conflict, kind, category, count`.
- 월별 집계는 누락 월을 0으로 채웁니다. DB 연결 시 로더만 동일한 내부 테이블 구조로 교체할 수 있습니다.

### Windows/Mac 공통 국기

국기 문자열은 `ui/flags.py`에서 로컬 Twemoji SVG 이미지로 변환합니다. 14개 분쟁의 국기 23종은
`assets/flags`에 포함되어 있으며 국기 렌더링에 외부 CDN이나 OS 이모지 글꼴이 필요하지 않습니다.
기본 크기는 20×20px, 간격은 4px이고 `assets/style.css`의 `.conflict-flag`, `.conflict-flags`에서 바꿉니다.
국가명 대체 텍스트와 원본 국가 순서를 유지하며, 빈 값은 생략하고 자산이 없는 국가는 문자 코드로 표시합니다.
출처·버전·해시는 `assets/flags/manifest.json`, 라이선스는 `LICENSE-GRAPHICS`에 있습니다.

#### 기존 원본의 DB 적재 전 정제 과제

아래 값은 이번 작업에서 삭제·변경하지 않았으며, 대시보드 집계와 별개로 DB 적재 전에 검토해야 합니다.

- 무기 사전에서 `EL`, `C-801`, `M-20`, `CS`가 서로 다른 범주에 존재합니다.
  이는 현재 `wp_name UNIQUE` 제약과 맞지 않습니다. 화면은 각 범주 안에서만 명칭을 중복 제거합니다.
- 사용 표현에 빈 `trans_form` 31행, 원형·활용형 쌍 중복 46행이 있습니다.
  원형·활용형 최대 길이는 각각 35자·36자로 현재 `varchar(20)`을 넘습니다.
  이 테이블은 기사 집계에 조인하지 않으며 로더는 이 기존 정제 과제를 허용합니다.

### 데이터 수집

1. SIPRI Arms Transfers Database – 무기 명칭·분류 데이터
   - 선정 사유 : 검증된 주요 재래식 무기의 명칭과 설명을 구조화하여 제공하므로 일관된 무기 분류 기준으로 활용하기에 적합
   - 수집 목적: 기사에 등장하는 무기 명칭을 표준 무기명과 분류에 연결하기 위한 무기 분류 Dictionary 구축
   - 수집 방법
     1. SIPRI Transfer Register 데이터를 CSV 형태로 수집
     2. `Weapon designation`과 `Weapon description`의 연결 관계를 추출하고 표기 차이·약어를 정리하여 `표준 무기명–무기 분류–검색용 명칭` 형태로 구성
2. NATO STO Science & Technology Trends 2020–2040 – 방산기술 기본 분류 데이터
   - 선정 사유: NATO 국방 과학기술 전문가 네트워크의 분석을 기반으로 주요 방산기술 범주를 체계적으로 제시하여 기술 분류 기준으로 활용하기에 적합
   - 수집 목적: 기사에 등장하는 방산기술 명칭을 공통 기술명과 상위 분류에 연결하기 위한 기술 분류 Dictionary 구축
   - 수집 방법
     1. NATO STO 기술전망 보고서의 8개 핵심 기술 분야를 대상으로 `Keywords`, `Technology Focus Areas`, 기술 정의 및 약어표에서 기술 용어 후보 추출
     2. 독립적인 기술 개념으로 사용할 수 있는 표현만 선정하고 기관명·정책명·국가명·연구 프로그램명 및 의미가 지나치게 넓은 일반 용어 제외
     3. NATO의 전자기전·자율체계·AI·양자기술 관련 공개자료에서 세부 기술과 운용 용어를 추가 추출
     4. 대소문자·하이픈·단수·복수 표기를 정규화하고 정식 명칭을 표준 기술명으로 지정하여 약어·표기 변형·한국어 번역명을 유의어로 연결
     5. 기존 용어와 추가 용어를 병합하여 `표준 기술명–상위 기술 분류–동의어·약어–한국어 번역명–출처` 형태의 기술 분류 Dictionary 구성
3. CAMEO Event Coding Dictionary 및 NATO 군사행동 정의 – 무기·기술 사용 여부 판별 데이터
   - 선정 사유: 위협·군사태세와 실제 공격·교전을 구분하는 정의와 사례를 제공하여 무기·기술의 사용 여부 판정 기준으로 활용하기에 적합
   - 수집 목적: 단순 언급·위협·계획과 실제 전투·방어·군사작전에서의 사용을 구분하기 위한 판별 Dictionary 구축
   - 수집 방법
     1. CAMEO에서 실제 군사행동과 사용 이전 단계에 해당하는 이벤트 코드 및 정의 수집
     2. 공개 Verb Pattern Dictionary에서 코드별 동사·구문을 추출하여 사용 포함·제외 표현 구성
     3. NATO 공개자료에서 전자전 등 방산기술의 운용 표현을 추가하여 `행동 유형–판별 표현–포함 여부–출처` 형태로 구성
4. GDELT 2.0 BigQuery – 해외 뉴스 기사 후보 데이터
   - 선정 사유: 다양한 해외 온라인 뉴스의 사건·출처·GDELT 처리 시각·원문 URL을 제공하여 수집 결과의 추적성 확보에 적합. 실제 기사 발행일은 원문에서 별도 확인
   - 수집 목적: 분쟁별·기간별 무기·방산기술 사용 보도 빈도와 변화 추이 분석을 위한 원천 기사 데이터 확보
   - 수집 방법
     1. UCDP의 국가 간 분쟁 목록과 검토가 필요한 잠정 후보를 구분하고, 2016~2026년 중 실행 시점까지 전체 기간을 한 번에 조회하는 분쟁별 검색 배치를 생성
     2. 공통 SQL에 각 배치의 기간·국가코드·행위자 검색어를 전달하고, `기간 AND (관련 지역 OR 행위자)` 조건으로 후보 조회. 매체·언어·이벤트 코드·추출 품질은 검토 정보로 보존
     3. `Events`와 `EventMentions`를 `GLOBALEVENTID`로 연결하여 웹 기사 URL을 확보하고, `batch_id`·`candidate_conflict_id`를 함께 저장
     4. 원문에서 실제 발행일과 해당 국가 간 직접 교전·무기 및 기술 사용 여부를 확인하여 내부 분쟁·일방적 폭력 등을 제외. 후보 분쟁 연결은 최종 판정 결과와 구분
     5. 기사 식별정보·원문 URL·사건 및 후보 분쟁 연결을 보존하고, 적용 SQL·파라미터·조회 기간·작업 ID·수집 일시를 기록하여 재현성 확보
